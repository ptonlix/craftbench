Codex 上下文到 80%，真没必要立刻 Handoff 新开 Session。

半年前，这么做确实是个好习惯。现在 Codex 自己的上下文压缩已经做得很好，继续跑，或者手动 /compact 一次，通常就够了。频繁压缩反而可能损失任务细节，也没法充分利用 Prompt Caching。

上下文到 80%，不等于模型只剩 20% 的脑子。

现在模型处理长上下文的能力已经很强，Harness 还会补充当前状态，最新任务又在 Prompt 末尾。只要任务主线没有乱，它通常知道眼下该做什么。

Handoff 当然还有价值。任务关系不大时，新开 Session 更干净。跨 Agent 接力时也很好用，比如 Claude Code 没做完的工作交给 Codex。不过我更习惯先在 Claude Code 里用 Fable 5 写技术方案，反复 Review 和修改，再把定稿交给 Codex，配合 /goal 按文档推进。

真正影响交付质量的，往往不是上下文占用了多少，而是验收标准写得有多清楚。

我之前做一个迁移任务，没有设严格验收，Codex 很快交了一个差强人意的版本。后来我把标准改成 UI 必须和原版像素级一致，它就开始每一步截图、对比差异、继续修，直到只剩可以忽略的偏差。

所以别一直盯着 80% 焦虑，也别指望 Handoff 解决所有上下文问题。把目标、边界和验证方法写清楚，让 Codex 能自己判断是否真的完成，通常比频繁人工接管更有效。

## 质检报告

**L1 硬性规则** ✅
- 正文禁用词、禁用标点、结构套话、空泛工具名均为 0 处
- 正文约 590 字，符合短文长度目标
- 无表演式情绪和陈词滥调结尾
- 段落结构清晰

**L2 风格一致性** ✅
- 反常识判断开头，第二段迅速给出原因
- 短段落推进，长短句有变化
- 使用 Codex、Handoff、Session、Prompt Caching、Harness、Claude Code、Fable 5、/compact、/goal 等具体对象
- 每段均在提供信息、案例或推进判断

**L3 活人感** ✅
- 使用用户提供的迁移任务和像素级验收经历，没有补造事实
- 作者视角明确，姿态自然
- 结尾落到可执行判断

**总评**：3 层全部通过
